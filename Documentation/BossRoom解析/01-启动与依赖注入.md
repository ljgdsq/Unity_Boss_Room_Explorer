## 1. Startup 场景里有什么

`Assets/Scenes/Startup.unity` 是**唯一一个永远不卸载的场景**，它的对象很少：

| 对象 | 组件 / 来源 | 作用 |
| --- | --- | --- |
| `ApplicationController` | `ApplicationController`（继承 `LifetimeScope`） | 根容器、注册所有全局服务、启动后加载 MainMenu |
| `NetworkingManager` | prefab：`NetworkManager` + `UnityTransport` | 网络核心 |
| `ConnectionManager` | prefab：连接状态机 | 见 [02](02-连接流程与状态机.md) |
| `SceneLoader` | prefab：`SceneLoaderWrapper` + loading 屏 | 场景加载门面 |
| `NetworkObjectPool` | prefab：网络对象池 | 投射物复用 |
| `GameDataSource` | prefab：全局配置 | 动作/角色数据 |
| `UpdateRunner` | `UpdateRunner` | 给"非 MonoBehaviour 的服务"提供 Update 心跳 |
| `UIMessageManager` | `ConnectionStatusMessageUIManager` 等 | 全局弹窗/提示 |
| `Main Camera`、`EventSystem`、`ClientMusicPlayer` | — | 常驻 UI/音频 |

关键点：**`Startup` 场景本身不是"菜单"，它是"运行时外壳"**。`ApplicationController.Start()` 把 `MainMenu` 加载进来（`Single` 模式），此后 `Startup` 里的对象靠 `DontDestroyOnLoad` 一直活着。

```csharp
// Assets/Scripts/ApplicationLifecycle/ApplicationController.cs:81
private void Start()
{
    m_LocalLobby = Container.Resolve<LocalLobby>();
    m_LobbyServiceFacade = Container.Resolve<LobbyServiceFacade>();
    ...
    DontDestroyOnLoad(gameObject);
    DontDestroyOnLoad(m_UpdateRunner.gameObject);
    Application.targetFrameRate = 120;
    SceneManager.LoadScene("MainMenu");   // 注意：这里用的是普通 SceneManager
}
```

> 第一次切场景用普通 `SceneManager` 是必须的：此时还没 StartHost/StartClient，`NetworkSceneManager` 尚未就绪。

## 2. VContainer 速成（只看这个项目用到的部分）

| 概念 | 在本项目中的样子 |
| --- | --- |
| `LifetimeScope` | `ApplicationController`（根）、各 `GameStateBehaviour`（子）。子 scope 能拿到父 scope 的所有注册 |
| `Configure(IContainerBuilder)` | 注册入口，**只注册不解析** |
| `builder.Register<T>(Lifetime.Singleton)` | 纯 C# 类单例（如 `LocalLobby`、`ProfileManager`） |
| `builder.RegisterComponent(mb)` | 注册一个场景里的 MonoBehaviour 实例 |
| `builder.RegisterInstance(obj).AsImplementedInterfaces()` | 直接塞一个已构造好的对象（消息通道） |
| `builder.RegisterEntryPoint<T>()` | 注册并**在容器构建完成后调用其 `Start()`**（`IStartable`） |
| `[Inject]` 方法/字段/属性 | 容器构建该对象时注入；MonoBehaviour 的 `[Inject]` 方法在场景 scope 建立时调用 |
| `IObjectResolver.Resolve<T>()` | 手动取（`ApplicationController.Start` 里用） |
| `CreateChild(builder => ...)` | 运行时创建子容器（`LobbyServiceFacade.Start` 用它隔离 `LobbyAPIInterface`） |

**为什么值得用**：Boss Room 里到处是"UI 需要拿到 ConnectionManager、LobbyServiceFacade、消息订阅者"。没有 DI 就得靠单例 + `FindObjectOfType`，而这两者在"场景切换 + 网络对象按需生成"的环境里非常脆。DI 让**依赖关系显式化**，也让 `NetcodeHooks` 这种桥接模式成为可能（见第 7 节）。

### 根容器的注册清单

```csharp
// ApplicationController.cs:37
protected override void Configure(IContainerBuilder builder)
{
    builder.RegisterComponent(m_UpdateRunner);
    builder.RegisterComponent(m_ConnectionManager);
    builder.RegisterComponent(m_NetworkManager);

    builder.Register<LocalLobbyUser>(Lifetime.Singleton);
    builder.Register<LocalLobby>(Lifetime.Singleton);
    builder.Register<ProfileManager>(Lifetime.Singleton);
    builder.Register<PersistentGameState>(Lifetime.Singleton);

    builder.RegisterInstance(new MessageChannel<QuitApplicationMessage>()).AsImplementedInterfaces();
    builder.RegisterInstance(new MessageChannel<UnityServiceErrorMessage>()).AsImplementedInterfaces();
    builder.RegisterInstance(new MessageChannel<ConnectStatus>()).AsImplementedInterfaces();
    builder.RegisterInstance(new MessageChannel<DoorStateChangedEventMessage>()).AsImplementedInterfaces();

    builder.RegisterComponent(new NetworkedMessageChannel<LifeStateChangedEventMessage>()).AsImplementedInterfaces();
    builder.RegisterComponent(new NetworkedMessageChannel<ConnectionEventMessage>()).AsImplementedInterfaces();

    builder.RegisterInstance(new MessageChannel<ReconnectMessage>()).AsImplementedInterfaces();
    builder.RegisterInstance(new BufferedMessageChannel<LobbyListFetchedMessage>()).AsImplementedInterfaces();

    builder.Register<AuthenticationServiceFacade>(Lifetime.Singleton);
    builder.RegisterEntryPoint<LobbyServiceFacade>(Lifetime.Singleton).AsSelf();
}
```

几个细节值得注意：

- **`LocalLobby` 是单例**：它比 MainMenu 的 UI 活得久，贯穿"创建房间 → 进 CharSelect → 进 BossRoom"。
- **`LobbyServiceFacade` 是 EntryPoint**：它的 `Start()` 需要容器已经建好才能 `CreateChild`，所以不能用普通构造。
- **`NetworkedMessageChannel<T>` 用 `RegisterComponent` 注册**：它不是 `NetworkBehaviour`，而是一个普通类（继承 `MessageChannel<T>`），靠 `[Inject]` 拿到 `NetworkManager` 来注册 named message handler。这里用 `RegisterComponent` 只是为了让容器对它做字段/方法注入。
- **iOS 代码裁剪**：注释写着 `Registering as instance to prevent code stripping on iOS`——泛型类型如果只通过反射使用，IL2CPP 可能裁掉它，直接 `new` 出来注册最稳。

## 3. UpdateRunner：给"不是 MonoBehaviour 的服务"一个心跳

`Assets/Scripts/Infrastructure/UpdateRunner.cs` 只有 100 行，但很实用。

**问题**：`LobbyServiceFacade` 需要每 1.5 秒发一次 lobby heartbeat，但它是个普通 C# 类，没有 `Update()`。

**方案**：一个常驻的 `MonoBehaviour` 维护订阅者表，支持**自定义周期**（不是每帧都调）：

```csharp
// UpdateRunner.cs:88
foreach (var subscriber in m_Subscribers)
{
    var subscriberData = m_SubscriberData[subscriber];
    if (Time.time >= subscriberData.NextCallTime)
    {
        subscriber.Invoke(Time.time - subscriberData.LastCallTime); // 传入"距上次调用的时间"
        subscriberData.LastCallTime = Time.time;
        subscriberData.NextCallTime = Time.time + subscriberData.Period;
    }
}
```

三个"防呆"设计：

1. **延迟生效**：`Subscribe/Unsubscribe` 只是把操作塞进 `m_PendingHandlers` 队列，下一帧 `Update` 开头统一执行。这样"在回调里退订自己"不会破坏 `HashSet` 的遍历。
2. **拒绝匿名函数/局部函数**：`onUpdate.Target == null` 或方法名含 `<` 直接报错——因为它们无法被 `Unsubscribe`，会造成永久泄漏。
3. **传入 `deltaTime`**：订阅者拿到的是"距上次调用过了多久"，而不是固定值，便于做与帧率无关的累加。

调用方（`LobbyServiceFacade.BeginTracking`）：

```csharp
m_UpdateRunner.Subscribe(DoLobbyHeartbeat, 1.5f);
```

> 这套模式在"services 层需要 tick"时非常通用，可以直接抄到自己的项目里。

## 4. 消息总线：`MessageChannel` / `BufferedMessageChannel` / `NetworkedMessageChannel`

位置：`Assets/Scripts/Infrastructure/PubSub/`

这是本项目**解耦 UI 与逻辑**的核心工具。三种通道对应三种需求：

| 类型 | 特点 | 典型用途 |
| --- | --- | --- |
| `MessageChannel<T>` | 纯本地、即时 | `ConnectStatus`（连接状态提示）、`ReconnectMessage` |
| `BufferedMessageChannel<T>` | 本地 + **缓存最后一条**，新订阅者立刻收到 | `LobbyListFetchedMessage`（UI 打开晚于数据到达也不会丢） |
| `NetworkedMessageChannel<T>` | 服务端 `Publish` 时**同时**通过 named message 广播给所有客户端 | `LifeStateChangedEventMessage`、`ConnectionEventMessage` |

### 4.1 接口

```csharp
public interface IPublisher<T> { void Publish(T message); }
public interface ISubscriber<T> { IDisposable Subscribe(Action<T> handler); }
```

订阅返回 `IDisposable`，配合 `DisposableGroup` 批量释放：

```csharp
// Gameplay/UI/ConnectionStatusMessageUIManager.cs:18
[Inject]
void InjectDependencies(ISubscriber<ConnectStatus> connectStatusSub, ISubscriber<ReconnectMessage> reconnectMessageSub)
{
    m_Subscriptions = new DisposableGroup();
    m_Subscriptions.Add(connectStatusSub.Subscribe(OnConnectStatus));
    m_Subscriptions.Add(reconnectMessageSub.Subscribe(OnReconnectMessage));
}
```

> 这个 `[Inject]` 方法在 **MonoBehaviour 被容器构建/场景 scope 建立时**调用，因此不需要 `Start` 里手动找依赖。

### 4.2 为什么 `MessageChannel` 要"待处理列表"

`Infrastructure/PubSub/MessageChannel.cs` 里用了一个 `Dictionary<Action<T>, bool> m_PendingHandlers`（true = 待添加，false = 待移除），真正的 `m_MessageHandlers` 列表只在 `Publish` 开头批量合并。原因：处理器内部可能再订阅/退订（例如弹窗关闭时退订），直接改正在遍历的列表会抛异常。

### 4.3 `NetworkedMessageChannel<T>` 的约束

```csharp
public class NetworkedMessageChannel<T> : NetworkBehaviour, IPublisher<T>, ISubscriber<T>
    where T : unmanaged, INetworkSerializeByMemcpy
```

- 泛型必须是 **unmanaged + memcpy 可序列化**（本质是 blittable struct），因为底层用 `CustomMessagingManager.SendNamedMessageToAll` 发原始字节。
- 服务端 `Publish`：先本地派发，再广播；客户端只注册 handler 接收。
- 因此**客户端不能 `Publish`**——它没有发送路径。这类消息天然是"服务端 → 客户端"的单向事件。

### 4.4 已注册的消息一览

| 消息 | 通道类型 | 发送方 | 用途 |
| --- | --- | --- | --- |
| `ConnectStatus` | 本地 | ConnectionManager 状态类 | UI 弹窗、UI 解锁 |
| `ReconnectMessage` | 本地 | ClientReconnectingState | "重连中 1/2" 弹窗 |
| `QuitApplicationMessage` | 本地 | UI | 退出游戏（先离开 Lobby） |
| `UnityServiceErrorMessage` | 本地 | Auth / Lobby 封装 | 云服务错误提示 |
| `LobbyListFetchedMessage` | 本地 Buffered | LobbyServiceFacade | 房间列表 UI |
| `DoorStateChangedEventMessage` | 本地 | 服务端门逻辑 | 门开/关（其实服务端本地派发） |
| `LifeStateChangedEventMessage` | **网络** | 服务端 | 玩家倒下/复活/Boss 死亡 → 消息流 + 游戏结束判定 |
| `ConnectionEventMessage` | **网络** | 服务端 | "xxx 加入了/离开了" |
| `CheatUsedMessage` | **网络**（仅编辑器/Dev） | 服务端 | 作弊提示 |

## 5. `NetworkObjectPool`：拦截 Netcode 的生成

位置：`Assets/Scripts/Infrastructure/NetworkObjectPool.cs`

Netcode 默认每次 `Spawn` 都 `Instantiate` 新对象，投射物这种高频对象会造成 GC 抖动。Boss Room 的做法是**接管 Netcode 的预制体工厂**：

```csharp
// NetworkObjectPool.cs:148
NetworkManager.Singleton.PrefabHandler.AddHandler(prefab, new PooledPrefabInstanceHandler(prefab, this));
```

`INetworkPrefabInstanceHandler` 只有两个方法：

```csharp
NetworkObject Instantiate(ulong ownerClientId, Vector3 position, Quaternion rotation); // 从池里取
void Destroy(NetworkObject networkObject);                                            // 放回池里
```

于是**服务端 Spawn 和客户端收到 spawn 消息时，都会走同一个池**，不需要在业务代码里区分端。

使用时：

```csharp
var instance = NetworkObjectPool.Singleton.GetNetworkObject(prefab, pos, rot);
instance.Spawn();                       // 服务端调用
// 回收由 Netcode 在 Despawn 时通过 handler 自动完成
```

> 注释里写了为什么小怪（Imp）不用池：**故意保留一个"原生 spawn vs 池化 spawn"的对照示例**。

## 6. `SceneLoaderWrapper`：场景加载的门面

位置：`Packages/com.unity.multiplayer.samples.coop/Utilities/SceneManagement/SceneLoaderWrapper.cs`

它把两种加载方式统一成一个 API：

```csharp
public void LoadScene(string sceneName, bool useNetworkSceneManager, LoadSceneMode loadSceneMode = LoadSceneMode.Single)
```

内部逻辑：

- `useNetworkSceneManager == true` 且 `NetworkConfig.EnableSceneManagement`：走 `NetworkManager.SceneManager.LoadScene`，并订阅 `OnSceneEvent` 控制 loading 进度条（`Load` / `LoadComplete` / `EventCompleted`），最后给客户端发 `ClientStopLoadingScreenRpc`。
- 否则：走普通 `UnityEngine.SceneManagement.SceneManager.LoadSceneAsync`，手动开关 loading 屏。
- 客户端在场景同步事件（`Synchronize`，且 `ClientSynchronizationMode == Single`）时，会调用 `UnloadAdditiveScenes()` 卸载除 active 之外的已加载场景——保证客户端场景集合和服务端一致。

**为什么要包一层**：
1. 加载屏逻辑只写一次；
2. **服务端/客户端加载时机不同**，`OnSceneEvent` 能拿到"谁加载完了、谁超时了"——`ServerBossRoomState` 正是靠 `OnLoadEventCompleted` 决定何时生成玩家角色（见 [04](04-场景与游戏状态.md)）。

> 注意它自己也是 `NetworkBehaviour` 且 `DontDestroyOnLoad`，因为要跨场景监听事件。

## 7. `NetcodeHooks`：让"非 NetworkBehaviour"也能用网络生命周期

位置：`Packages/com.unity.multiplayer.samples.coop/Utilities/Net/NetcodeHooks.cs`

```csharp
public class NetcodeHooks : NetworkBehaviour
{
    public event Action OnNetworkSpawnHook;
    public event Action OnNetworkDespawnHook;
    public override void OnNetworkSpawn()  { base.OnNetworkSpawn();  OnNetworkSpawnHook?.Invoke(); }
    public override void OnNetworkDespawn(){ base.OnNetworkDespawn();OnNetworkDespawnHook?.Invoke(); }
}
```

**要解决的问题**：`GameStateBehaviour` 本身就是个 `LifetimeScope`（MonoBehaviour），它很想在"网络对象生成后"做初始化（比如 `ServerBossRoomState` 订阅 NetworkManager 回调），但它**不能**再继承 `NetworkBehaviour`（C# 单继承，已经被 `LifetimeScope` 占了）。

**方案**：在同一个 GameObject 上挂一个 `NetcodeHooks`，把事件转出来：

```csharp
// Gameplay/GameState/ServerBossRoomState.cs 的 OnNetworkSpawn 绑定
m_NetcodeHooks.OnNetworkSpawnHook += OnNetworkSpawn;
m_NetcodeHooks.OnNetworkDespawnHook += OnNetworkDespawn;
```

注释里还提到另一个理由：**dedicated server 上某些 NetworkBehaviour 会被剥离，导致 NetworkBehaviour 索引错位**，把"网络生命周期"和"业务逻辑"拆开更安全。

这是本项目里非常值得学的一个小模式。

## 8. `GameDataSource`：所有配置的入口

位置：`Assets/Scripts/Gameplay/GameplayObjects/RuntimeDataContainers/GameDataSource.cs`

职责很简单但很关键：

1. 持有所有 `CharacterClass`（ScriptableObject），按 `CharacterTypeEnum` 建索引；
2. 持有所有 `Action` 原型（ScriptableObject），**在 `Awake` 时给每个 Action 分配 `ActionID`**；
3. 提供 `GetActionPrototypeByID(ActionID)`。

```csharp
// GameDataSource.cs:138
void BuildActionIDs()
{
    var uniqueActions = new HashSet<Action>(m_ActionPrototypes);
    uniqueActions.Add(GeneralChaseActionPrototype);
    ...
    int i = 0;
    foreach (var uniqueAction in uniqueActions)
    {
        uniqueAction.ActionID = new ActionID { ID = i };
        m_AllActions.Add(uniqueAction);
        i++;
    }
}
```

**为什么用 `HashSet` 再编号**：避免同一个 SO 被拖进多个列表导致 ID 重复。ID 只是"数组下标"，**不落盘**，每次启动重新生成——所以联机双方必须用同一份配置（同一构建）。

> 这也是"网络传输里只发 `ActionID`（整数）而不是 Action 资源引用"的前提，见 [05](05-动作系统.md)。
